第 5 章

型検査アルゴリズム

型付け規則は、どの判断が成り立つかを述べるが、その確かめ方までは教えてくれない。本章では、仕事を相互再帰する二つの関数に分けて規則をアルゴリズムに変え、一方が項の型を計算し、もう一方が定義的等価を使ってその型を期待される型と比較する。できあがるのは、数十行の Rust である。

規則からアルゴリズムへ

図 3.1 の八つの規則のうち七つは構文主導（syntax-directed）であり、項を見ればどの規則が当てはまるか分かる。宇宙なら T-Sort、変数なら T-Var、Π\PiΠ なら T-Pi、λ\lambdaλ なら T-Lam、適用なら T-App が適用される。例外は T-Conv であり、この規則はどの項にもどの時点でも適用できるため、項を見ただけではいつ使うべきか分からない。導出を素朴に探索しようとすれば、当て推量に頼ることになる。

標準的な解決策 [Barendregt 1992] は、型検査を二つの関数に分けることである。

  • Infer(Γ,t)\Infer(\Gamma, t)Infer(Γ,t) は、構文主導の規則に従って Γ\GammaΓ における ttt の型を一つ計算し、計算できなければ失敗する。
  • Check(Γ,t,T)\Check(\Gamma, t, T)Check(Γ,t,T) は、ttt が期待される型 TTT をもつことを確かめる関数で、型を推論してそれを定義的等価で TTT と比較する。

T-Conv が適用されるのは、Check\CheckCheck の内部のただ一箇所である。このほかに、型が特定の形をしていなければならない場所が二つあり、T-App における Π\PiΠ と、T-Pi および T-Lam の前提における宇宙である。そこでアルゴリズムは、推論した型を、いちばん外側の形が見える程度まで計算する。

アルゴリズムは項に対する二つの関数を使うが、その定義は 第 12 章 に先送りする。

  • Whnf(T)\Whnf(T)Whnf(T) は、いちばん外側の形が見えるまで TTT を計算する。たとえば Whnf(Id  (P→P))=P→P\Whnf(\mathit{Id}\;(P \to P)) = P \to PWhnf(Id(P→P))=P→P であり、これは Π\PiΠ である。
  • IsDefEq(A,B)\IsDefEq(A, B)IsDefEq(A,B) は A≡BA \conv BA≡B を決定する。

アルゴリズム

アルゴリズム 5.1 は、Rust に近い擬似コードで書かれている。Infer\InferInfer の各ケースには、それが実装する規則を注記してある。

アルゴリズム 5.1. 型推論と型検査。

Infer(Γ, t):
  if t = Sort u:                                        -- T-Sort
      return Sort (u + 1)
  if t = x:                                             -- T-Var
      if (x : A) ∈ Γ: return A  else fail "unbound variable"
  if t = Π(x : A). B:                                   -- T-Pi
      u ← InferSort(Γ, A)
      (x', B') ← Freshen(Γ, x, B)
      v ← InferSort((Γ, x' : A), B')
      return Sort (imax(u, v))
  if t = λ(x : A). s:                                   -- T-Lam
      InferSort(Γ, A)
      (x', s') ← Freshen(Γ, x, s)
      B ← Infer((Γ, x' : A), s')
      return Π(x' : A). B
  if t = f a:                                           -- T-App
      T ← Whnf(Infer(Γ, f))
      if T = Π(x : A). B:
          Check(Γ, a, A)
          return B[x ↦ a]
      else fail "not a function"

Check(Γ, t, T):                                         -- T-Conv
  T' ← Infer(Γ, t)
  if IsDefEq(T', T): return  else fail "type mismatch"

InferSort(Γ, A):
  T ← Whnf(Infer(Γ, A))
  if T = Sort u: return u  else fail "expected a type"

Freshen(Γ, x, b):
  if x ∈ dom(Γ):
      choose x' ∉ dom(Γ) ∪ FV(b)
      return (x', b[x ↦ x'])
  else return (x, b)

このアルゴリズムには次の性質がある。

  • 構文主導である。 Infer\InferInfer の各ケースは、図 3.1 の規則のちょうど一つに対応する。証明を見つけるのは難しくても、与えられた証明を検査するのは機械的な作業であり、選択を迫られる場面は一度もない。
  • T-Conv が単独で適用されることはない。 適用されるのは Check\CheckCheck の内部だけであり、推論した型と期待される型が出会う場所はそこしかない。
  • InferSort\InferSortInferSort は、カーネルがある項を型とみなすかどうかを決める手段である。 項 AAA が型であるのは、その型が宇宙に計算されるとき、そのときに限る。たとえば λ\lambdaλ 抽象は、推論される型が必ず Π\PiΠ になるので、決して型にならない。
  • Freshen\FreshenFreshen は C-Ext の付帯条件を実装する。 文脈にすでにある名前をもつ束縛子を改名する。第 11 章 では、この段階を省くとカーネルが不健全になる項を示す。
  • 文脈は整形式のままである。 仮定が追加されるのはその型に対する InferSort\InferSortInferSort が成功した後に限られるので、空の文脈から始めると、アルゴリズムが作る文脈はすべて整形式になる。空でない文脈から始める呼び出し側は、その文脈を別途検査しなければならない。
  • 停止性は Whnf\WhnfWhnf と IsDefEq\IsDefEqIsDefEq が停止することに依存するが、正しく型付けされた項については、強正規化（第 14 章）によってこれが成り立つ。

Infer\InferInfer と Check\CheckCheck への分割は、情報が二つの向きに流れることから、双方向（bidirectional）型検査と呼ばれることがある。推論は葉から上へ進み、変数の型や適用を構成する部分から、項全体の型を求める。一方、検査では利用者が与えた期待される型を下へ伝え、根で推論した型と比較する。私たちのカーネルではどの項も型を推論できるので、検査は推論に一回の比較を加えるだけでよいが、より豊かな体系には、期待される型があれば検査できても、型を推論できない項もある。

コードでは

アルゴリズム 5.1 は src/typecheck.rs の Kernel::infer、Kernel::check、Kernel::infer_sort である。Freshen は同じファイルの補助関数 rename_binder_if_needed にあたる。infer の全体を、第 II 部で加わる定数のケースも含めて以下に示すので、一行ずつ比べたいときに開いてほしい。

infer 関数の全体（約 50 行） 
pub fn infer(&self, ctx: &Context, t: &Term) -> Result<Term> {
    match t {
        // T-Sort
        Term::Sort(u) => Ok(Term::Sort(u.checked_add(1).ok_or("universe overflow")?)),
        // T-Var
        Term::Var(x) => ctx
            .iter()
            .rev()
            .find(|(name, _)| name == x)
            .map(|(_, ty)| ty.clone())
            .ok_or_else(|| format!("unbound local: {x}")),
        // T-Const（第 7 章）
        Term::Const(c) => self
            .decls
            .get(c)
            .map(|decl| decl.ty.clone())
            .ok_or_else(|| format!("unknown constant: {c}")),
        // T-Pi: Sort 0 は非述語的である。
        Term::Pi(x, domain, body) => {
            let domain_level = self.infer_sort(ctx, domain)?;
            let (x, body) = rename_binder_if_needed(ctx, x, body);
            let mut extended = ctx.clone();
            extended.push((x, (**domain).clone()));
            let body_level = self.infer_sort(&extended, &body)?;
            Ok(Term::Sort(if body_level == 0 {
                0
            } else {
                domain_level.max(body_level)
            }))
        }
        // T-Lam
        Term::Lam(x, domain, body) => {
            self.infer_sort(ctx, domain)?;
            let (x, body) = rename_binder_if_needed(ctx, x, body);
            let mut extended = ctx.clone();
            extended.push((x.clone(), (**domain).clone()));
            let body_type = self.infer(&extended, &body)?;
            Ok(Term::Pi(x, domain.clone(), Box::new(body_type)))
        }
        // T-App
        Term::App(f, a) => match self.whnf(&self.infer(ctx, f)?)? {
            Term::Pi(x, domain, codomain) => {
                self.check(ctx, a, &domain)?;
                Ok(subst(&codomain, &x, a))
            }
            ty => Err(format!("application of non-function: {ty:?}")),
        },
    }
}

擬似コードと異なる点がいくつかある。

  • 変数のケースの文脈探索は、末尾から（.rev()）探す。rename_binder_if_needed が名前の重複を防ぐので一致する項目が二つ以上あることはないが、呼び出し側が重複した名前を含む文脈を渡した場合には、末尾から探すのが正しい振る舞いである。
  • T-Pi の imax\imaximax は if body_level == 0 の式であり、本体が命題であるような Π\PiΠ は命題、そうでなければ二つのレベルの大きいほうに属する。
  • 宇宙レベルは u64 で、checked_add がオーバーフローを防ぐ。レベル 2642^{64}264 に近づく証明は現実には存在しないが、カーネルはどんな入力に対しても未定義動作を起こしてはならない。
  • 適用のケースは、擬似コードと同じく、f の推論された型にマッチする前に whnf を呼ぶが、これがなければ、型が Id  (A→B)\mathit{Id}\;(A \to B)Id(A→B) と書かれた関数を適用できない。

残りの二つの関数は短い。

/// Gamma |- t : expected。T-Conv を使って推論した型を比較する。
pub fn check(&self, ctx: &Context, t: &Term, expected: &Term) -> Result<()> {
    self.infer_sort(ctx, expected)?;
    let actual = self.infer(ctx, t)?;
    if self.is_def_eq(&actual, expected)? {
        Ok(())
    } else {
        Err(format!("type mismatch: actual {actual:?}, expected {expected:?}"))
    }
}

/// t の型を推論し、それが宇宙 Sort u であることを要求する。u を返す。
pub fn infer_sort(&self, ctx: &Context, t: &Term) -> Result<u64> {
    match self.whnf(&self.infer(ctx, t)?)? {
        Term::Sort(u) => Ok(u),
        other => Err(format!("expected a type, got {other:?}")),
    }
}

check は、期待される型そのものが型であることを確認するため、infer_sort(ctx, expected) から始まり、これは T-Conv の前提 Γ⊢B:Sort u\Gamma \vdash B : \Sort{u}Γ⊢B:Sortu にあたる。アルゴリズム内部では検査済みの型しか渡さないため、擬似コードではこの処理を省いたが、公開された check は利用者が書いた主張も受け取るので、Rust 版では検査している。

最後に Freshen である。

fn rename_binder_if_needed(ctx: &Context, x: &str, body: &Term) -> (String, Term) {
    if !ctx.iter().any(|(name, _)| name == x) {
        return (x.into(), body.clone());
    }
    let mut used = all_names(body);
    for (name, ty) in ctx {
        used.insert(name.clone());
        used.extend(all_names(ty));
    }
    let renamed = fresh(x, &used);
    let renamed_body = subst(body, x, &var(&renamed));
    (renamed, renamed_body)
}

避けるべき名前の集合は、擬似コードの dom(Γ)∪FV(b)\dom(\Gamma) \cup \FV(b)dom(Γ)∪FV(b) より大きく、本体と文脈中の型に現れる名前を、束縛か自由かを問わずすべて含む。必要以上に多くの名前を避けても害はなく、改名後の項が読みやすく保たれる。fresh は未使用になるまでプライム記号を付け足すので、x が衝突すれば x' になる。

Infer の実行を見る

下のエクスプローラは、項に対してアルゴリズムを走らせ、再帰呼び出しをすべて記録するので、Infer\InferInfer のどのケースに入ったか、どの文脈で、何を返したかが分かる。注記には、Whnf\WhnfWhnf が Π\PiΠ を露わにしたり、Freshen\FreshenFreshen が束縛子を改名したりといった、表に出ない仕事が記される。文脈欄には Q : Sort 0; q : Q のように、セミコロンで区切って仮定を書ける。

証明はどう検査されるか

項 ttt が定理 TTT を証明することを確かめるには、カーネルは空の文脈で Check(⋅,t,T)\Check(\cdot, t, T)Check(⋅,t,T) を実行する。スクリプト言語ではこれが qed の仕事であり、第 10 章 のタクティクが項を組み立て、qed がそれを goal で与えられた主張とともに check に渡す。その間にあるものはすべて信頼されていない。

次の章では、いくつかの項に対して Infer\InferInfer と Check\CheckCheck を手で実行するが、そのなかには、正しく型付けされているが、主張したものを証明していない項も含まれる。

演習

Infer(⋅,λ(A:Sort 1). λ(a:A). a)\Infer(\cdot, \tLam{A}{\Sort{1}}{\tLam{a}{A}{a}})Infer(⋅,λ(A:Sort1).λ(a:A).a) をトレースし、結果とその宇宙を答えよ。

解答

InferSort(⋅,Sort 1)\InferSort(\cdot, \Sort{1})InferSort(⋅,Sort1) は 222 を返し、文脈は A:Sort 1A : \Sort{1}A:Sort1 になる。内側の λ\lambdaλ では、InferSort(A:Sort 1,A)\InferSort(A : \Sort{1}, A)InferSort(A:Sort1,A) が 111 を返し、文脈は A:Sort 1,a:AA : \Sort{1}, a : AA:Sort1,a:A になり、Infer\InferInfer は本体に対して AAA を返す。したがって内側の結果は Π(a:A). A\tPi{a}{A}{A}Π(a:A).A、外側の結果は Π(A:Sort 1). Π(a:A). A\tPi{A}{\Sort{1}}{\tPi{a}{A}{A}}Π(A:Sort1).Π(a:A).A である。この型に InferSort\InferSortInferSort を走らせると imax(2,imax(1,1))=2\imax(2, \imax(1, 1)) = 2imax(2,imax(1,1))=2 となるので、この型は Sort 2\Sort{2}Sort2 に属する。

Π\PiΠ 型は「ただの型」なのに、なぜ Infer\InferInfer の Π\PiΠ のケースは Freshen\FreshenFreshen を呼ぶのか。これを省くと結果が変わる項を挙げよ。

解答

Π\PiΠ の本体は拡張された文脈で検査されるので、λ\lambdaλ と同じシャドーイングの問題が起きる。Γ=x:Sort 0,y:x\Gamma = x : \Sort{0}, y : xΓ=x:Sort0,y:x のとき、型 Π(x:Sort 1). y\tPi{x}{\Sort{1}}{y}Π(x:Sort1).y は失敗すべきである。y:xy : xy:x の xxx は外側の命題であり、命題は宇宙ではないからである。改名しなければ、末尾からの探索で内側の x:Sort 1x : \Sort{1}x:Sort1 が先に見つかり、yyy の型が Sort 1\Sort{1}Sort1 に値をもつかのように見えて、結果が誤る。改名すれば内側の束縛子は x′x'x′ になり、本体は依然として外側の xxx を指す。

覚えておくこと

  • Infer\InferInfer は項の形に従い、Check\CheckCheck は推論してから IsDefEq\IsDefEqIsDefEq で比較する。T-Conv が現れるのは Check\CheckCheck の内部だけである。
  • Whnf\WhnfWhnf は、Π\PiΠ や宇宙が要求される場所で、型のいちばん外側の形を露わにする。
  • InferSort\InferSortInferSort は「この項は型か」という検査であり、その型が宇宙に計算されなければならない。
  • Freshen\FreshenFreshen は、文脈の項目をシャドーイングしてしまう束縛子を改名し、これは便宜ではなく、正しさのための要件である。
  • src/typecheck.rs はアルゴリズムの直訳であり、約 100 行である。
