Chapter 8

Inductive Types II: The General Recipe

Chapter 7 built the recursor for the natural numbers by hand. In Lean, a user never does that: they write an inductive declaration, and the kernel checks it and generates the type former, the constructors, the recursor, and its computation rules. This chapter develops that procedure in three steps, from more constructors to parameters to indices, and then states it in general. The kernel's own code for it is about five hundred lines.

More constructors: trees

Nat\NatNat has two constructors, and only one of them has a recursive argument. Consider a type with three:

inductive Tree where
  | leaf   : Tree
  | node   : Tree -> Tree
  | branch : Tree -> Tree -> Tree

For example, branch  (node  leaf)  leaf\mathsf{branch}\;(\mathsf{node}\;\mathsf{leaf})\;\mathsf{leaf}branch(nodeleaf)leaf is a tree built from four constructors. To build M  tM\;tMt for every tree ttt, where M:Tree→Sort vM : \mathsf{Tree} \to \Sort{v}M:Tree→Sortv, the recipe of Chapter 7 asks for one case per constructor, and each argument of type Tree\mathsf{Tree}Tree contributes one induction hypothesis:

mleaf:M  leafmnode:Π(t:Tree). M  t→M  (node  t)mbranch:Π(l:Tree). Π(r:Tree). M  l→M  r→M  (branch  l  r)\begin{array}{lcl} m_{\mathsf{leaf}} &:& M\;\mathsf{leaf} \\[2pt] m_{\mathsf{node}} &:& \tPi{t}{\mathsf{Tree}}{M\;t \to M\;(\mathsf{node}\;t)} \\[2pt] m_{\mathsf{branch}} &:& \tPi{l}{\mathsf{Tree}}{\tPi{r}{\mathsf{Tree}}{M\;l \to M\;r \to M\;(\mathsf{branch}\;l\;r)}} \end{array}mleaf​mnode​mbranch​​:::​MleafΠ(t:Tree).Mt→M(nodet)Π(l:Tree).Π(r:Tree).Ml→Mr→M(branchlr)​

With MMM a predicate (v=0v = 0v=0), the same recursor is structural induction on trees. In general, a type with nnn constructors gets a recursor with nnn minor premises m1,…,mnm_1, \ldots, m_nm1​,…,mn​, and the kernel needs no code specific to the type: it only needs to know, for each constructor, which case to pick and which arguments to recurse on.

Here is that tree as the kernel sees it. Each box is a constructor application; the recursive fields hang below it, and the line at the bottom of each box is the recursor case that handles it, with (R  l)(R\;l)(Rl) and (R  r)(R\;r)(Rr) the induction hypotheses computed by recursive calls. Type another tree to see its cases.

inductive Tree : Sort 1 where
  | leaf
  | node (t : Tree)
  | branch (l : Tree) (r : Tree)
inductive Tree : Sort 1 where
  | leaf
  | node (t : Tree)
  | branch (l : Tree) (r : Tree)

def add : Nat -> Nat -> Nat := fun (m : Nat) => fun (n : Nat) => Nat.rec1 (fun (_n : Nat) => Nat) m (fun (k : Nat) => fun (r : Nat) => Nat.succ r) n
def one : Nat := Nat.succ Nat.zero
def four : Nat := Nat.succ (Nat.succ (Nat.succ one))

# The minor premise for branch takes l, r, then the two induction hypotheses.
def count : Tree -> Nat := fun (t : Tree) => Tree.rec1 (fun (_t : Tree) => Nat) one (fun (t : Tree) => fun (i : Nat) => Nat.succ i) (fun (l : Tree) => fun (r : Tree) => fun (i : Nat) => fun (j : Nat) => Nat.succ (add i j)) t

goal Eq Nat (count (Tree.branch (Tree.node Tree.leaf) Tree.leaf)) four
rfl
qed

Parameters: lists

A list of numbers is either empty or a number in front of a list of numbers, so we could declare a type ListNat\mathsf{ListNat}ListNat with constructors nil\mathsf{nil}nil and cons:Nat→ListNat→ListNat\mathsf{cons} : \Nat \to \mathsf{ListNat} \to \mathsf{ListNat}cons:Nat→ListNat→ListNat. But then lists of trees would need another declaration, ListTree\mathsf{ListTree}ListTree, with the same constructors and a separate recursor, and so on for every element type. It is better to make the element type an argument of the type itself:

inductive List (A : Sort 1) where
  | nil  : List A
  | cons : A -> List A -> List A

Now List  Nat\mathsf{List}\;\NatListNat and List  Tree\mathsf{List}\;\mathsf{Tree}ListTree are two instances of one declaration. The declaration adds

List:Sort 1→Sort 1,nil:Π(A:Sort 1). List  A,cons:Π(A:Sort 1). A→List  A→List  A.\mathsf{List} : \Sort{1} \to \Sort{1}, \qquad \mathsf{nil} : \tPi{A}{\Sort{1}}{\mathsf{List}\;A}, \qquad \mathsf{cons} : \tPi{A}{\Sort{1}}{A \to \mathsf{List}\;A \to \mathsf{List}\;A}.List:Sort1→Sort1,nil:Π(A:Sort1).ListA,cons:Π(A:Sort1).A→ListA→ListA.

The constructors take AAA as an explicit first argument. For example, the one-element list [5][5][5] is cons  Nat  5  (nil  Nat)\mathsf{cons}\;\Nat\;5\;(\mathsf{nil}\;\Nat)consNat5(nilNat). Within one list, AAA never changes: the tail of cons  A  a  as\mathsf{cons}\;A\;a\;\mathit{as}consAaas is again a List  A\mathsf{List}\;AListA. An argument of the type that stays the same in every constructor and every recursive argument is called a parameter. Because it never changes, the recursor can take it once, before the motive, and treat it as fixed:

The rules ignore the parameter A′A'A′ stored in the constructor; in a well-typed term it is convertible to AAA. For example, the length of a list is

length:=λ(A:Sort 1). λ(x:List  A). List.rec1  A  (λ(_:List  A). Nat)  zero  (λ(a:A). λ(as:List  A). λ(r:Nat). succ  r)  x.\mathit{length} \mathrel{:=} \tLam{A}{\Sort{1}}{\tLam{x}{\mathsf{List}\;A}{ \mathsf{List.rec}_1\;A\;(\tLam{\_}{\mathsf{List}\;A}{\Nat})\;\zero\;(\tLam{a}{A}{\tLam{\mathit{as}}{\mathsf{List}\;A}{\tLam{r}{\Nat}{\suc\;r}}})\;x}}.length:=λ(A:Sort1).λ(x:ListA).List.rec1​A(λ(_:ListA).Nat)zero(λ(a:A).λ(as:ListA).λ(r:Nat).succr)x.

Indices: vectors

A List  Nat\mathsf{List}\;\NatListNat may have any length. What if we want the length to be part of the type, so that Vec  Nat  0\mathsf{Vec}\;\Nat\;0VecNat0 and Vec  Nat  2\mathsf{Vec}\;\Nat\;2VecNat2 are different types?

inductive Vec (A : Sort 1) : Nat -> Sort 1 where
  | vnil  : Vec A 0
  | vcons : (n : Nat) -> A -> Vec A n -> Vec A (succ n)

The element type AAA is still a parameter. The length is not: vnil\mathsf{vnil}vnil has length 000, and vcons\mathsf{vcons}vcons takes a vector of length nnn and returns one of length succ  n\suc\;nsuccn. An argument of the type that may differ between constructors, and between a constructor and its recursive arguments, is called an index. The constructors are

vnil:Π(A:Sort 1). Vec  A  zero,vcons:Π(A:Sort 1). Π(n:Nat). A→Vec  A  n→Vec  A  (succ  n).\mathsf{vnil} : \tPi{A}{\Sort{1}}{\mathsf{Vec}\;A\;\zero}, \qquad \mathsf{vcons} : \tPi{A}{\Sort{1}}{\tPi{n}{\Nat}{A \to \mathsf{Vec}\;A\;n \to \mathsf{Vec}\;A\;(\suc\;n)}}.vnil:Π(A:Sort1).VecAzero,vcons:Π(A:Sort1).Π(n:Nat).A→VecAn→VecA(succn).

Because an index varies, the recursor cannot fix it in advance. Instead, the motive takes it as an argument, M:Π(n:Nat). Vec  A  n→Sort vM : \tPi{n}{\Nat}{\mathsf{Vec}\;A\;n \to \Sort{v}}M:Π(n:Nat).VecAn→Sortv, and the case for vcons\mathsf{vcons}vcons is

Π(n:Nat). Π(a:A). Π(xs:Vec  A  n). M  n  xs→M  (succ  n)  (vcons  A  n  a  xs).\tPi{n}{\Nat}{\tPi{a}{A}{\tPi{\mathit{xs}}{\mathsf{Vec}\;A\;n}{M\;n\;\mathit{xs} \to M\;(\suc\;n)\;(\mathsf{vcons}\;A\;n\;a\;\mathit{xs})}}}.Π(n:Nat).Π(a:A).Π(xs:VecAn).Mnxs→M(succn)(vconsAnaxs).

The induction hypothesis is about a vector of length nnn, read off the type Vec  A  n\mathsf{Vec}\;A\;nVecAn of the recursive argument, and the conclusion is about one of length succ  n\suc\;nsuccn, read off the result type of the constructor. The script examples/generic-vec.leanmini (Appendix E) declares this type and checks a small term that uses it.

The general recipe

This section states the procedure for a single inductive type with parameters and indices. Mutual and nested inductive types, which Lean also supports, are out of scope.

The procedure also answers a question that T-Const leaves open. A constant without a body is an assumption: T-Const would accept c:Π(P:Sort 0). Pc : \tPi{P}{\Sort{0}}{P}c:Π(P:Sort0).P just as readily as zero:Nat\zero : \Natzero:Nat, and with it the system would be inconsistent. The constants generated below are not arbitrary assumptions. They are instances of a fixed schema, the inductive types of the Calculus of Inductive Constructions, whose consistency is known [Werner 1994].

Telescopes. We write (x⃗:A⃗)(\vec{x} : \vec{A})(x:A) for a sequence of bindings (x1:A1)⋯(xk:Ak)(x_1 : A_1) \cdots (x_k : A_k)(x1​:A1​)⋯(xk​:Ak​) in which each AiA_iAi​ may mention x1,…,xi−1x_1, \ldots, x_{i-1}x1​,…,xi−1​; Π(x⃗:A⃗). B\tPi{\vec{x}}{\vec{A}}{B}Π(x:A).B for Π(x1:A1). ⋯ Π(xk:Ak). B\tPi{x_1}{A_1}{\cdots\,\tPi{x_k}{A_k}{B}}Π(x1​:A1​).⋯Π(xk​:Ak​).B; and f  x⃗f\;\vec{x}fx for f  x1⋯xkf\;x_1 \cdots x_kfx1​⋯xk​. The length of x⃗\vec{x}x is ∣x⃗∣|\vec{x}|∣x∣. In the code, a telescope is a Context, and telescope(binders, tail) in src/term.rs builds the nested Π\PiΠ.

Declarations. A declaration introduces a type former III and constructors c1,…,cnc_1, \ldots, c_nc1​,…,cn​:

I:Π(p⃗:P⃗). Π(ı⃗:J⃗). Sort ucj:Π(p⃗:P⃗). Π(a⃗:A⃗j). I  p⃗  t⃗j(j=1,…,n)\begin{array}{rcll} I &:& \tPi{\vec{p}}{\vec{P}}{\tPi{\vec{\imath}}{\vec{J}}{\Sort{u}}} & \\[2pt] c_j &:& \tPi{\vec{p}}{\vec{P}}{\tPi{\vec{a}}{\vec{A}_j}{I\;\vec{p}\;\vec{t}_j}} & (j = 1, \ldots, n) \end{array}Icj​​::​Π(p​:P).Π(:J).SortuΠ(p​:P).Π(a:Aj​).Ip​tj​​(j=1,…,n)​

The parameters p⃗\vec{p}p​ are shared by all constructors and appear unchanged in every result type. The indices ı⃗\vec{\imath} may differ between constructors: the index terms t⃗j\vec{t}_jtj​ may mention p⃗\vec{p}p​ and the constructor's own arguments a⃗\vec{a}a, which are called its fields. Acceptance. The kernel accepts a declaration only if the following four conditions hold.

  1. The type of III is a type in the current signature.
  2. With III added to the signature, each constructor type is a type, and it ends in I  p⃗  t⃗jI\;\vec{p}\;\vec{t}_jIp​tj​, where p⃗\vec{p}p​ are exactly the parameters in order and III does not occur in t⃗j\vec{t}_jtj​.
  3. Strict positivity. Each field type either does not mention III, or has the form Π(y⃗:B⃗). I  p⃗  s⃗\tPi{\vec{y}}{\vec{B}}{I\;\vec{p}\;\vec{s}}Π(y​:B).Ip​s where III occurs neither in B⃗\vec{B}B nor in s⃗\vec{s}s. A field of the second form is recursive.
  4. Universes. If u≥1u \ge 1u≥1, each field type lies in some Sort w\Sort{w}Sortw with w≤uw \le uw≤u. If u=0u = 0u=0, there is no condition.

Condition 2 lets the recursor treat the parameters uniformly. Condition 3 rules out declarations such as

inductive Bad where
  | mk : (Bad -> False) -> Bad

whose field mentions Bad to the left of an arrow. Case analysis on Bad would let one define f:Bad→Falsef : \mathsf{Bad} \to \mathsf{False}f:Bad→False by f  (mk  g)=g  (mk  g)f\;(\mathsf{mk}\;g) = g\;(\mathsf{mk}\;g)f(mkg)=g(mkg). Then f  (mk  f)f\;(\mathsf{mk}\;f)f(mkf) is a closed term of type False\mathsf{False}False, and it reduces to itself, so it has no normal form. For a type Tree\mathsf{Tree}Tree under declaration, some field types and their status are:

A field of type Nat→Tree\Nat \to \mathsf{Tree}Nat→Tree is a tree with infinitely many children, one for each number; the recursor can still recurse into each child ak  na_k\;nak​n. A field of type Tree→Nat\mathsf{Tree} \to \NatTree→Nat consumes trees instead of containing them, and it is the shape that makes Bad paradoxical.

Condition 4 prevents a type from containing a larger universe. Without it, a declaration T:Sort 1T : \Sort{1}T:Sort1 with a constructor mk:Sort 1→T\mathsf{mk} : \Sort{1} \to Tmk:Sort1→T would place a copy of all of Sort 1\Sort{1}Sort1 inside Sort 1\Sort{1}Sort1, which is the self-containment that Chapter 13 shows to be inconsistent. For u=0u = 0u=0 no condition is needed, because Sort 0\Sort{0}Sort0 is impredicative.

The final arguments are the indices and the element xxx itself, the major premise.

The rules. For each constructor, the kernel generates one iota-rule, which applies the minor premise to the fields and to the induction hypotheses, computed by recursive calls:

I.recv  p⃗  M  m⃗  ı⃗  (cj  p⃗ ′  a⃗)  →ι  mj  a⃗  h⃗,hk=λ(y⃗:B⃗). I.recv  p⃗  M  m⃗  s⃗  (ak  y⃗).I.\mathsf{rec}_v\;\vec{p}\;M\;\vec{m}\;\vec{\imath}\;(c_j\;\vec{p}\,'\;\vec{a}) \;\iotared\; m_j\;\vec{a}\;\vec{h}, \qquad h_k = \tLam{\vec{y}}{\vec{B}}{I.\mathsf{rec}_v\;\vec{p}\;M\;\vec{m}\;\vec{s}\;(a_k\;\vec{y})}.I.recv​p​Mm(cj​p​′a)→ι​mj​ah,hk​=λ(y​:B).I.recv​p​Mms(ak​y​).

The major premise is at position ∣p⃗∣+1+n+∣ı⃗∣|\vec{p}| + 1 + n + |\vec{\imath}|∣p​∣+1+n+∣∣ (counting from zero), the constructor has ∣p⃗∣|\vec{p}|∣p​∣ parameters and ∣a⃗∣|\vec{a}|∣a∣ fields, and in a well-typed redex p⃗ ′\vec{p}\,'p​′ is convertible to p⃗\vec{p}p​, so the rule ignores it, as the rules for lists ignore A′A'A′. For Nat\NatNat, Tree\mathsf{Tree}Tree, List\mathsf{List}List, and Vec\mathsf{Vec}Vec the procedure produces exactly the recursors and rules of this chapter and the last, and the recursor types agree with the ones Lean 4 generates, up to the names of bound variables and implicit arguments.

Eliminating from propositions. If u≥1u \ge 1u≥1, the recursor is generated for every level vvv. If u=0u = 0u=0, so that III is a proposition, the recursor is generated only for v=0v = 0v=0, unless III is a subsingleton: it has at most one constructor, and each field either is a proof (its type lies in Sort 0\Sort{0}Sort0) or occurs among the index terms t⃗j\vec{t}_jtj​. The restriction keeps data from depending on which proof of a proposition was given. For example, P∨QP \vee QP∨Q has two constructors, so a function from proofs of P∨QP \vee QP∨Q into Nat\NatNat could return 000 for one and 111 for the other, and a proof would carry computational information. Lean's Or.rec and Exists.rec therefore eliminate only into Prop, while And.rec and Eq.rec eliminate into every universe: And has one constructor whose fields are proofs, and Eq (Chapter 9) has one constructor with no fields.

So the kernel's rules stay fixed while the signature grows: one generic procedure turns each declaration into signature entries, and a single reduction function runs their rules (Chapter 12).

In the code

The procedure lives in src/inductive/. The input is an InductiveSpec (src/declaration.rs): the name, the parameter and index telescopes, the universe level uuu, and one ConstructorSpec per constructor giving its fields and its index terms t⃗j\vec{t}_jtj​. The script parser builds this from an inductive block.

  • Kernel::add_inductive in src/inductive/mod.rs runs the four acceptance conditions in order (check_inductive_type is condition 1, check_constructor_fields checks that fields are types and enforces condition 4, check_constructor_result is condition 2) and, if all pass, registers the type former and constructors and records an InductiveInfo. On failure the signature is left unchanged.
  • src/inductive/positivity.rs is condition 3. check_recursive_field peels the leading Π\PiΠs of a field type, rejecting any whose domain mentions III, and requires the target to be III applied to exactly the parameter variables followed by index terms that do not mention III. It returns a RecursiveFieldInfo recording y⃗:B⃗\vec{y} : \vec{B}y​:B and s⃗\vec{s}s, which is all the recursor generator needs.
  • src/inductive/recursor.rs builds the recursor type from the formula above. recursor_type assembles the telescope p⃗\vec{p}p​, the motive, the minor premises, the indices, and the major premise; minor_premise_type builds each CjC_jCj​; induction_hypothesis_type builds each Hj,kH_{j,k}Hj,k​. The generated binder names (__motive, __minor_j, __ih_j_k, __major) start with two underscores, which user declarations may not use, so they can never clash with fields.
  • allows_large_elimination in mod.rs implements the subsingleton test. add_inductive registers I.rec0 always and I.rec1 when large elimination is allowed; register_recursor generates higher levels on demand.

The iota-rules are not generated as terms. whnf applies them directly from the stored InductiveInfo, which Chapter 12 explains.

The heart of the generator is short enough to read in full. Compare it with the formula for CjC_jCj​.

/// C_j = Pi (as : As_j). Pi (hs : Hs_j). M ts_j (c_j ps as)
fn minor_premise_type(info: &InductiveInfo, j: usize, constructor: &ConstructorInfo) -> Term {
    // c_j ps as
    let constructor_application = apps(
        const_term(&constructor.name),
        info.params.iter().chain(constructor.fields.iter()).map(|(name, _)| var(name)),
    );
    // (as : As_j) followed by (hs : Hs_j)
    let mut minor_premise_binders = constructor.fields.clone();
    for (k, recursive_field) in constructor.recursive_fields.iter().enumerate() {
        minor_premise_binders.push((
            format!("{INDUCTION_HYPOTHESIS_PREFIX}{j}_{k}"),
            induction_hypothesis_type(constructor, recursive_field),
        ));
    }
    telescope(&minor_premise_binders, apply_motive(&constructor.result_indices, constructor_application))
}

The kernel never special-cases Nat\NatNat. Kernel::standard in src/kernel.rs declares Nat\NatNat and Eq\mathsf{Eq}Eq by calling add_inductive with the same InductiveSpec a user script would produce, so Figure 7.1 is generated, not hard-coded, and the tests in src/inductive/tests.rs check that the generated types agree with the hand-written ones.

The positivity check is a soundness requirement, not a convenience. Lean, Coq, and Agda have each had bugs over the years in this part of the kernel, because the general case (nested and mutual inductives, universe constraints, indices mentioning other inductives) is complicated. Our restricted schema keeps the check to eighty lines. When extending it, the question to ask of every new feature is: can a value of the type be built from a function that consumes the type?

Exercises

Write the recursor type Bool.recv\mathsf{Bool.rec}_vBool.recv​ for inductive Bool where | true | false, and define negation with it.

Solution

Which of the four acceptance conditions rejects each of the following, if any? (a) inductive T : Sort 1 where | mk (f : Sort 1). (b) inductive T : Sort 1 where | mk (f : T -> T). (c) inductive T : Sort 0 where | mk (f : Sort 1).

Solution

(a) Condition 4: the field Sort 1\Sort{1}Sort1 has type Sort 2\Sort{2}Sort2, which exceeds u=1u = 1u=1. (b) Condition 3: TTT occurs to the left of an arrow in a field type. (c) Accepted: for u=0u = 0u=0 condition 4 imposes nothing, and the type is a proposition that packs up a type; this is the impredicativity of Sort 0\Sort{0}Sort0 at work, and it is harmless because TTT eliminates only into Sort 0\Sort{0}Sort0 (it is not a subsingleton, since its field is neither a proof nor an index).

What to remember

  • A declaration gives a type former with parameters and indices, and constructors with fields. Parameters are fixed throughout; indices vary and become arguments of the motive.
  • The recursor has one minor premise per constructor, with one induction hypothesis per recursive field, and one iota-rule per constructor.
  • Acceptance requires well-formedness, uniform parameters, strict positivity, and a universe bound. Positivity is what keeps recursion terminating and the logic consistent.
  • Propositions eliminate only into Sort 0\Sort{0}Sort0 unless they are subsingletons.
  • The kernel generates all of this from data; it contains no code specific to Nat\NatNat.
