Chapter 2

The Language of Terms

Before a kernel can check anything, it needs a precise language of terms. Ours has five kinds of term, and that is enough to express propositional logic with quantification over propositions. This chapter fixes the grammar, the notational conventions used for the rest of the book, and the Rust type that represents terms.

Five kinds of terms

The core language is a small dependent type theory. Its terms are generated by the grammar

t,A,B  ::=  Sort u  ∣  x  ∣  Π(x:A). B  ∣  λ(x:A). t  ∣  t  st, A, B \;::=\; \Sort{u} \;\mid\; x \;\mid\; \tPi{x}{A}{B} \;\mid\; \tLam{x}{A}{t} \;\mid\; t\;st,A,B::=Sortu∣x∣Π(x:A).B∣λ(x:A).t∣ts

where uuu is a natural number and xxx is a variable name. Each form has a role.

  • Sort u\Sort{u}Sortu is a universe: a type whose elements are themselves types. The number uuu is its level. Sort 0\Sort{0}Sort0 is the universe of propositions. Chapter 13 explains why there is a whole hierarchy rather than a single universe.
  • xxx is a variable. Its meaning comes from the context in which it appears, either a λ\lambdaλ or Π\PiΠ binder enclosing it or an assumption in the typing context.
  • Π(x:A). B\tPi{x}{A}{B}Π(x:A).B is a Π\PiΠ-type, the dependent function type from Chapter 1. It is the type of functions that take an x:Ax : Ax:A and return something of type BBB, where BBB may mention xxx.
  • λ(x:A). t\tLam{x}{A}{t}λ(x:A).t is a λ\lambdaλ-abstraction, a function that takes an argument xxx of type AAA and returns ttt.
  • t  st\;sts is application of ttt to sss.

The grammar makes no distinction between types and terms. The proposition Π(P:Sort 0). P→P\tPi{P}{\Sort{0}}{P \to P}Π(P:Sort0).P→P and its proof λ(P:Sort 0). λ(p:P). p\tLam{P}{\Sort{0}}{\tLam{p}{P}{p}}λ(P:Sort0).λ(p:P).p are both terms built from the same five constructors:

λ(P:Sort 0). λ(p:P). p⏟proof:Π(P:Sort 0). P→P⏟proposition, the type of the proof.\underbrace{\tLam{P}{\Sort{0}}{\tLam{p}{P}{p}}}_{\text{proof}} \quad : \quad \underbrace{\tPi{P}{\Sort{0}}{P \to P}}_{\text{proposition, the type of the proof}}.proofλ(P:Sort0).λ(p:P).p​​:proposition, the type of the proofΠ(P:Sort0).P→P​​.

The same two terms, seen as trees, make the shared grammar visible. Every node is one of the five constructors; the name on a Π\PiΠ or λ\lambdaλ node is the variable it binds. Click a node to see the subterm it stands for, or type another term.

Whether a term is a valid type is not a syntactic property. It is decided by the type checker: a term is a type exactly when its own type is a universe (Chapter 5).

Part II adds one more form, the constant ccc, which names something declared in the kernel's signature, such as Nat\mathsf{Nat}Nat or Nat.succ\mathsf{Nat.succ}Nat.succ. Constants behave like free variables whose types come from a global table, and they are never bound. Everything in Part I works without them, so they are introduced when needed, in Chapter 7. The Rust type below already includes them.

Conventions

The book uses the following letters consistently.

Letters Stand for
s,t,a,b,fs, t, a, b, fs,t,a,b,f and A,B,C,TA, B, C, TA,B,C,T (possibly primed or subscripted) terms
x,y,zx, y, zx,y,z and any name bound by Π\PiΠ or λ\lambdaλ variable names
u,v,wu, v, wu,v,w universe levels
Γ\GammaΓ typing contexts (Chapter 3)
Σ\SigmaΣ the signature of constants (Chapter 7)

Three abbreviations keep terms readable.

Arrows. When BBB does not mention xxx, we write A→BA \to BA→B for Π(x:A). B\tPi{x}{A}{B}Π(x:A).B. Ordinary function types are thus a special case of dependent function types, and implication is a special case of universal quantification. In the implementation the binder of an arrow is the reserved name _.

Associativity. Application associates to the left and arrows to the right:

f  a  b  =  (f  a)  b,A→B→C  =  A→(B→C).f\;a\;b \;=\; (f\;a)\;b, \qquad A \to B \to C \;=\; A \to (B \to C).fab=(fa)b,A→B→C=A→(B→C).

Currying. A function of two arguments is a function that takes the first argument and returns a function waiting for the second. For example, λ(a:A). λ(b:B). a\tLam{a}{A}{\tLam{b}{B}{a}}λ(a:A).λ(b:B).a has type A→B→AA \to B \to AA→B→A, and applying it to x:Ax : Ax:A and y:By : By:B is written

(λ(a:A). λ(b:B). a)  x  y  =  ((λ(a:A). λ(b:B). a)  x)  y.(\tLam{a}{A}{\tLam{b}{B}{a}})\;x\;y \;=\; ((\tLam{a}{A}{\tLam{b}{B}{a}})\;x)\;y.(λ(a:A).λ(b:B).a)xy=((λ(a:A).λ(b:B).a)x)y.

The two associativity conventions are designed to fit together: a curried function of type A→B→CA \to B \to CA→B→C applied as f  a  bf\;a\;bfab needs no parentheses on either side.

Currying is why the whole language needs only one-argument functions. A proof of A→B→CA \to B \to CA→B→C is a function that, given a proof of AAA, returns a proof of B→CB \to CB→C, which is itself a function. "Assume AAA and BBB" becomes two nested assumptions, and the two λ\lambdaλs in the proof term mirror them.

Binding and scope

In λ(x:A). t\tLam{x}{A}{t}λ(x:A).t and Π(x:A). B\tPi{x}{A}{B}Π(x:A).B, the variable xxx is bound, and its scope is the body ttt or BBB. The annotation AAA is outside the scope: in λ(x:x). x\tLam{x}{x}{x}λ(x:x).x the xxx in the annotation refers to something outside the term, while the xxx in the body refers to the argument. A variable occurrence that is not inside the scope of a binder for it is free. For example, in λ(x:P). f  x  y\tLam{x}{P}{f\;x\;y}λ(x:P).fxy the variables PPP, fff, and yyy are free and xxx is bound.

Two facts about bound variables matter throughout the book, and both are formalized in Chapter 11.

  1. The name of a bound variable carries no meaning: λ(x:A). x\tLam{x}{A}{x}λ(x:A).x and λ(y:A). y\tLam{y}{A}{y}λ(y:A).y are the same function. Terms that differ only in the names of bound variables are called alpha-equivalent, and a kernel must treat them as equal.
  2. Replacing a variable by a term, which the typing rules and computation both require, must not accidentally bring a free variable under a binder of the same name. Getting this right is called capture-avoiding substitution.

Both facts are easy to state and both have caused real bugs in real proof checkers, which is why they get their own chapter.

In the code

Terms are the Rust enum Term in src/term.rs. There is one variant per kind of term, plus the constants of Part II.

#[derive(Clone, Debug, PartialEq, Eq)]
pub enum Term {
    Sort(u64),                          // Sort u
    Var(String),                        // x        (local, bound or in the context)
    Const(String),                      // c        (global, from the signature)
    Pi(String, Box<Term>, Box<Term>),   // Pi (x : A). B
    Lam(String, Box<Term>, Box<Term>),  // fun (x : A). b
    App(Box<Term>, Box<Term>),          // f a
}

Variables are represented by their names as strings, and binders store the bound name. This is the most direct representation and the easiest to read; it is also the one that makes the naming problems of Chapter 11 unavoidable, which is deliberate, because the point of the book is to see those problems and solve them.

The same file provides small constructor functions so that terms can be written without nested Box::new calls: var("x"), const_term("Nat"), app(f, a), pi("x", a, b), lam("x", a, b), and arrow(a, b), which builds pi("_", a, b). Three helpers encode the conventions of this chapter directly.

/// f a_1 ... a_n   (left-associated application)
pub fn apps(f: Term, args: impl IntoIterator<Item = Term>) -> Term {
    args.into_iter().fold(f, app)
}

/// Pi (x_1 : A_1) ... Pi (x_k : A_k). tail   (a telescope of binders)
pub fn telescope(binders: &[(String, Term)], tail: Term) -> Term {
    binders.iter().rev().fold(tail, |body, (name, ty)| pi(name, ty.clone(), body))
}

/// Decomposes t into its spine: a head that is not an application, and its arguments.
/// f a b  becomes  (f, [a, b]);  a non-application becomes  (t, []).
pub fn spine(t: &Term) -> (Term, Vec<Term>) {
    match t {
        Term::App(f, a) => {
            let (head, mut args) = spine(f);
            args.push((**a).clone());
            (head, args)
        }
        _ => (t.clone(), vec![]),
    }
}

apps and spine are inverses of each other: apps(h, args) builds the left-nested application h  a1⋯anh\;a_1 \cdots a_nha1​⋯an​, and spine takes it apart again. The spine view is how the reduction engine of Chapter 12 looks at a term, so get comfortable with it now. The nested term ((f  a)  b)  c((f\;a)\;b)\;c((fa)b)c has head fff and arguments [a,b,c][a, b, c][a,b,c]; walking down the function side of each application reaches the head, and the arguments collected on the way, read from the inside out, are in the right order.

The surface syntax of the .leanmini scripts used throughout the book writes the same terms as Sort 0, forall (x : A), B, A -> B, fun (x : A) => b, and juxtaposition for application. Appendix E gives the full grammar.

Exercises

Write the proposition "for all propositions PPP and QQQ, PPP implies QQQ implies PPP" as a term, and give a proof term for it.

Solution

The proposition is Π(P:Sort 0). Π(Q:Sort 0). P→Q→P\tPi{P}{\Sort{0}}{\tPi{Q}{\Sort{0}}{P \to Q \to P}}Π(P:Sort0).Π(Q:Sort0).P→Q→P, which unfolds to Π(P:Sort 0). Π(Q:Sort 0). Π(_:P). Π(_:Q). P\tPi{P}{\Sort{0}}{\tPi{Q}{\Sort{0}}{\tPi{\_}{P}{\tPi{\_}{Q}{P}}}}Π(P:Sort0).Π(Q:Sort0).Π(_:P).Π(_:Q).P. A proof is λ(P:Sort 0). λ(Q:Sort 0). λ(p:P). λ(q:Q). p\tLam{P}{\Sort{0}}{\tLam{Q}{\Sort{0}}{\tLam{p}{P}{\tLam{q}{Q}{p}}}}λ(P:Sort0).λ(Q:Sort0).λ(p:P).λ(q:Q).p. In leanmini syntax:

goal forall (P : Sort 0), forall (Q : Sort 0), P -> Q -> P
exact fun (P : Sort 0) => fun (Q : Sort 0) => fun (p : P) => fun (q : Q) => p
qed

Fully parenthesize f  a  (g  b)  cf\;a\;(g\;b)\;cfa(gb)c and A→(B→C)→DA \to (B \to C) \to DA→(B→C)→D, then give the spine of the first term.

Solution

f  a  (g  b)  c=((f  a)  (g  b))  cf\;a\;(g\;b)\;c = ((f\;a)\;(g\;b))\;cfa(gb)c=((fa)(gb))c, with head fff and arguments [a,  g  b,  c][a,\; g\;b,\; c][a,gb,c]. Note that g  bg\;bgb stays a single argument because of the parentheses. A→(B→C)→D=A→((B→C)→D)A \to (B \to C) \to D = A \to ((B \to C) \to D)A→(B→C)→D=A→((B→C)→D), which is Π(_:A). Π(_:(Π(_:B). C)). D\tPi{\_}{A}{\tPi{\_}{(\tPi{\_}{B}{C})}{D}}Π(_:A).Π(_:(Π(_:B).C)).D.

In λ(x:A). λ(y:x). λ(x:Sort 0). y\tLam{x}{A}{\tLam{y}{x}{\tLam{x}{\Sort{0}}{y}}}λ(x:A).λ(y:x).λ(x:Sort0).y, which occurrences of xxx refer to which binder? Which variables are free?

Solution

The xxx in the annotation of yyy refers to the outer binder λ(x:A)\lambda(x : A)λ(x:A), because the inner λ(x:Sort 0)\lambda(x : \Sort{0})λ(x:Sort0) has not been entered yet. The innermost xxx is bound by the inner binder but never used. The only free variable is AAA. This term reappears in Chapter 11, where it breaks a type checker that handles shadowing carelessly.

What to remember

  • Terms are universes Sort u\Sort{u}Sortu, variables, Π\PiΠ-types, λ\lambdaλ-abstractions, and applications. Types and terms share one grammar.
  • A→BA \to BA→B abbreviates a Π\PiΠ-type whose body ignores its variable. Application is left-associative, arrows are right-associative, and functions are curried.
  • Bound variable names are arbitrary, and substitution must avoid capture. Both are handled in Chapter 11.
  • In Rust, Term is an enum with one variant per form, and spine/apps convert between nested applications and a head with an argument list.
