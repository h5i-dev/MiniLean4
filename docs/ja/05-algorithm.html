第 5 章

型検査アルゴリズム

この章では、型付け規則を実際に判定できる手順に書き直します。互いに呼び合う二つの関数のうち、infer が項の型を求め、check がそれを定義的等価で期待される型と比べます。Rust で実装しても数十行です。

規則からアルゴリズムへ

図 3.1 の八つの規則のうち七つは構文主導（syntax-directed）で、項を見ればどの規則を使うかが決まります。宇宙なら T-Sort、変数なら T-Var、Π\PiΠ なら T-Pi、λ\lambdaλ なら T-Lam、適用なら T-App です。例外は T-Conv で、この規則はどの項にもいつでも適用できるので、項を見ただけではいつ使えばよいか分かりません。導出を素朴に探索すると、当て推量に頼るしかなくなります。

標準的な解決策は、型検査を二つの関数に分けることです [Barendregt 1992]。

  • Infer(Γ,t)\Infer(\Gamma, t)Infer(Γ,t) は、構文主導の規則に従って Γ\GammaΓ における ttt の型を一つ計算し、計算できなければ失敗します。
  • Check(Γ,t,T)\Check(\Gamma, t, T)Check(Γ,t,T) は、ttt が期待される型 TTT をもつことを確かめます。具体的には型を推論し、それを定義的等価で TTT と比較します。

T-Conv を使うのは Check\CheckCheck の内部の一箇所だけです。これとは別に、型が特定の形をしていなければならない場所が二つあります。T-App では Π\PiΠ が、T-Pi と T-Lam の前提では宇宙が必要です。そこでアルゴリズムは、推論した型をいちばん外側の形が見えるところまで計算します。

アルゴリズムは項に対する次の二つの関数を使います。定義は 第 12 章 で与えます。

  • Whnf(T)\Whnf(T)Whnf(T) は、いちばん外側の形が見えるまで TTT を計算します。たとえば Whnf(Id  (P→P))=P→P\Whnf(\mathit{Id}\;(P \to P)) = P \to PWhnf(Id(P→P))=P→P で、結果は Π\PiΠ です。
  • IsDefEq(A,B)\IsDefEq(A, B)IsDefEq(A,B) は A≡BA \conv BA≡B を決定します。

型検査アルゴリズム

アルゴリズム 5.1 に、Rust に近い擬似コードで全体を示します。Infer\InferInfer の各ケースには、対応する規則を注記しました。

アルゴリズム 5.1. 型推論と型検査。

Infer(Γ, t):
  if t = Sort u:                                        -- T-Sort
      return Sort (u + 1)
  if t = x:                                             -- T-Var
      if (x : A) ∈ Γ: return A  else fail "unbound variable"
  if t = Π(x : A). B:                                   -- T-Pi
      u ← InferSort(Γ, A)
      (x', B') ← Freshen(Γ, x, B)
      v ← InferSort((Γ, x' : A), B')
      return Sort (imax(u, v))
  if t = λ(x : A). s:                                   -- T-Lam
      InferSort(Γ, A)
      (x', s') ← Freshen(Γ, x, s)
      B ← Infer((Γ, x' : A), s')
      return Π(x' : A). B
  if t = f a:                                           -- T-App
      T ← Whnf(Infer(Γ, f))
      if T = Π(x : A). B:
          Check(Γ, a, A)
          return B[x ↦ a]
      else fail "not a function"

Check(Γ, t, T):                                         -- T-Conv
  T' ← Infer(Γ, t)
  if IsDefEq(T', T): return  else fail "type mismatch"

InferSort(Γ, A):
  T ← Whnf(Infer(Γ, A))
  if T = Sort u: return u  else fail "expected a type"

Freshen(Γ, x, b):
  if x ∈ dom(Γ):
      choose x' ∉ dom(Γ) ∪ FV(b)
      return (x', b[x ↦ x'])
  else return (x, b)

このアルゴリズムには次の性質があります。

  • 構文主導です。 Infer\InferInfer の各ケースは、図 3.1 の規則のちょうど一つに対応します。証明を見つけるのは難しくても、与えられた証明の検査は機械的な作業で、どこにも選択の余地はありません。
  • T-Conv が単独で使われることはありません。 使うのは Check\CheckCheck の内部だけで、推論した型と期待される型が出会うのはそこしかないからです。
  • ある項を型とみなすかどうかは InferSort\InferSortInferSort が決めます。 項 AAA が型であるのは、その型が宇宙に計算されるとき、かつそのときに限ります。たとえば λ\lambdaλ 抽象は、推論される型が必ず Π\PiΠ になるので、決して型にはなりません。
  • Freshen\FreshenFreshen は C-Ext の付帯条件を実装します。 文脈にすでにある名前を束縛子が使っていれば、その束縛子を改名します。第 11 章 では、この手順を省くとカーネルが不健全になる例を示します。
  • 文脈は整形式に保たれます。 仮定を文脈に追加するのは、その型に対する InferSort\InferSortInferSort が成功した後だけです。そのため空の文脈から始めれば、アルゴリズムが作る文脈はすべて整形式になります。空でない文脈から呼び出す場合は、呼び出し側がその文脈を別途検査しなければなりません。
  • 停止性は Whnf\WhnfWhnf と IsDefEq\IsDefEqIsDefEq の停止に依存します。正しく型付けされた項については、強正規化（第 14 章）によってこれが保証されます。

Infer\InferInfer と Check\CheckCheck への分割は、情報が二つの向きに流れることから、双方向（bidirectional）型検査と呼ばれることがあります。推論では情報が葉から上へ流れ、変数の型や適用の各部分から項全体の型を組み立てます。一方、検査では利用者が与えた期待される型を下へ伝え、根で推論した型と比較します。私たちのカーネルではどの項の型も推論できるので、検査は推論に比較を一回足すだけで済みます。ただ、より豊かな体系には、期待される型があれば検査はできるのに、型を推論できない項もあります。

コードでは

アルゴリズム 5.1 に対応するのは、src/typecheck.rs の Kernel::infer、Kernel::check、Kernel::infer_sort です。Freshen は同じファイルの補助関数 rename_binder_if_needed にあたります。以下に infer の全体を、第 II 部で加わる定数のケースも含めて載せておくので、擬似コードと一行ずつ見比べたいときに開いてください。

infer 関数の全体（約 50 行） 
pub fn infer(&self, ctx: &Context, t: &Term) -> Result<Term> {
    match t {
        // T-Sort
        Term::Sort(u) => Ok(Term::Sort(u.checked_add(1).ok_or("universe overflow")?)),
        // T-Var
        Term::Var(x) => ctx
            .iter()
            .rev()
            .find(|(name, _)| name == x)
            .map(|(_, ty)| ty.clone())
            .ok_or_else(|| format!("unbound local: {x}")),
        // T-Const（第 7 章）
        Term::Const(c) => self
            .decls
            .get(c)
            .map(|decl| decl.ty.clone())
            .ok_or_else(|| format!("unknown constant: {c}")),
        // T-Pi: Sort 0 は非述語的である。
        Term::Pi(x, domain, body) => {
            let domain_level = self.infer_sort(ctx, domain)?;
            let (x, body) = rename_binder_if_needed(ctx, x, body);
            let mut extended = ctx.clone();
            extended.push((x, (**domain).clone()));
            let body_level = self.infer_sort(&extended, &body)?;
            Ok(Term::Sort(if body_level == 0 {
                0
            } else {
                domain_level.max(body_level)
            }))
        }
        // T-Lam
        Term::Lam(x, domain, body) => {
            self.infer_sort(ctx, domain)?;
            let (x, body) = rename_binder_if_needed(ctx, x, body);
            let mut extended = ctx.clone();
            extended.push((x.clone(), (**domain).clone()));
            let body_type = self.infer(&extended, &body)?;
            Ok(Term::Pi(x, domain.clone(), Box::new(body_type)))
        }
        // T-App
        Term::App(f, a) => match self.whnf(&self.infer(ctx, f)?)? {
            Term::Pi(x, domain, codomain) => {
                self.check(ctx, a, &domain)?;
                Ok(subst(&codomain, &x, a))
            }
            ty => Err(format!("application of non-function: {ty:?}")),
        },
    }
}

擬似コードとの違いがいくつかあります。

  • 変数のケースでは、文脈を末尾から（.rev()）探します。rename_binder_if_needed が名前の重複を防ぐので、一致する項目が二つ以上見つかることはありません。それでも呼び出し側が重複した名前を含む文脈を渡した場合には、末尾から探すのが正しい振る舞いです。
  • T-Pi の imax\imaximax は if body_level == 0 の式で実現しています。本体が命題なら Π\PiΠ も命題になり、そうでなければ二つのレベルの大きいほうに属します。
  • 宇宙レベルは u64 で表し、checked_add でオーバーフローを防いでいます。レベルが 2642^{64}264 に近づく証明は現実にはありえませんが、カーネルはどんな入力に対しても未定義動作を起こしてはいけません。
  • 適用のケースでは、擬似コードと同じく、f の推論された型をマッチする前に whnf を呼びます。これがないと、型が Id  (A→B)\mathit{Id}\;(A \to B)Id(A→B) と書かれた関数を適用できません。

残りの二つの関数は短く済みます。

/// Gamma |- t : expected。T-Conv を使って推論した型を比較する。
pub fn check(&self, ctx: &Context, t: &Term, expected: &Term) -> Result<()> {
    self.infer_sort(ctx, expected)?;
    let actual = self.infer(ctx, t)?;
    if self.is_def_eq(&actual, expected)? {
        Ok(())
    } else {
        Err(format!("type mismatch: actual {actual:?}, expected {expected:?}"))
    }
}

/// t の型を推論し、それが宇宙 Sort u であることを要求する。u を返す。
pub fn infer_sort(&self, ctx: &Context, t: &Term) -> Result<u64> {
    match self.whnf(&self.infer(ctx, t)?)? {
        Term::Sort(u) => Ok(u),
        other => Err(format!("expected a type, got {other:?}")),
    }
}

check は最初に infer_sort(ctx, expected) を呼び、期待される型そのものが型であることを確かめます。これは T-Conv の前提 Γ⊢B:Sort u\Gamma \vdash B : \Sort{u}Γ⊢B:Sortu にあたります。アルゴリズムの内部では検査済みの型しか渡さないので擬似コードでは省きましたが、公開された check は利用者が書いた主張も受け取るため、Rust 版では検査しています。

最後は Freshen です。

fn rename_binder_if_needed(ctx: &Context, x: &str, body: &Term) -> (String, Term) {
    if !ctx.iter().any(|(name, _)| name == x) {
        return (x.into(), body.clone());
    }
    let mut used = all_names(body);
    for (name, ty) in ctx {
        used.insert(name.clone());
        used.extend(all_names(ty));
    }
    let renamed = fresh(x, &used);
    let renamed_body = subst(body, x, &var(&renamed));
    (renamed, renamed_body)
}

避ける名前の集合は擬似コードの dom(Γ)∪FV(b)\dom(\Gamma) \cup \FV(b)dom(Γ)∪FV(b) より大きく、本体と文脈中の型に現れる名前を、束縛されているか自由かを問わずすべて含みます。必要以上に多くの名前を避けても害はなく、むしろ改名後の項が読みやすくなります。fresh は未使用の名前になるまでプライム記号を付け足すので、x が衝突すれば x' になります。

Infer の実行を見る

下のエクスプローラは、項に対してアルゴリズムを走らせ、再帰呼び出しをすべて記録します。Infer\InferInfer のどのケースに、どの文脈で入り、何を返したかを追えます。注記には、Whnf\WhnfWhnf が Π\PiΠ を露わにする、Freshen\FreshenFreshen が束縛子を改名する、といった表に出ない処理が表示されます。文脈欄には、Q : Sort 0; q : Q のようにセミコロン区切りで仮定を書けます。

証明はどう検査されるか

項 ttt が定理 TTT の証明になっているかを確かめるには、カーネルは空の文脈で Check(⋅,t,T)\Check(\cdot, t, T)Check(⋅,t,T) を実行します。スクリプト言語でこれを担うのが qed です。第 10 章 のタクティクが項を組み立て、qed がその項を goal で与えた主張と一緒に check に渡します。その途中にあるものは、どれも信頼する必要がありません。

次の章では、いくつかの項に対して Infer\InferInfer と Check\CheckCheck を手で実行します。そのなかには、型は正しく付くのに、主張したものを証明していない項も含まれます。

演習

Infer(⋅,λ(A:Sort 1). λ(a:A). a)\Infer(\cdot, \tLam{A}{\Sort{1}}{\tLam{a}{A}{a}})Infer(⋅,λ(A:Sort1).λ(a:A).a) をトレースし、結果とその宇宙を答えてください。

解答

InferSort(⋅,Sort 1)\InferSort(\cdot, \Sort{1})InferSort(⋅,Sort1) が 222 を返し、文脈は A:Sort 1A : \Sort{1}A:Sort1 になります。内側の λ\lambdaλ では、InferSort(A:Sort 1,A)\InferSort(A : \Sort{1}, A)InferSort(A:Sort1,A) が 111 を返して文脈が A:Sort 1,a:AA : \Sort{1}, a : AA:Sort1,a:A になり、Infer\InferInfer は本体に対して AAA を返します。したがって内側の結果は Π(a:A). A\tPi{a}{A}{A}Π(a:A).A、外側の結果は Π(A:Sort 1). Π(a:A). A\tPi{A}{\Sort{1}}{\tPi{a}{A}{A}}Π(A:Sort1).Π(a:A).A です。この型に InferSort\InferSortInferSort を走らせると imax(2,imax(1,1))=2\imax(2, \imax(1, 1)) = 2imax(2,imax(1,1))=2 となるので、この型は Sort 2\Sort{2}Sort2 に属します。

Π\PiΠ 型は「ただの型」なのに、Infer\InferInfer の Π\PiΠ のケースではなぜ Freshen\FreshenFreshen を呼ぶのでしょうか。これを省くと結果が変わってしまう項を挙げてください。

解答

Π\PiΠ の本体も拡張された文脈で検査されるので、λ\lambdaλ と同じシャドーイングの問題が起きます。Γ=x:Sort 0,y:x\Gamma = x : \Sort{0}, y : xΓ=x:Sort0,y:x のとき、型 Π(x:Sort 1). y\tPi{x}{\Sort{1}}{y}Π(x:Sort1).y の検査は失敗すべきです。y:xy : xy:x の xxx は外側の命題で、命題は宇宙ではないからです。ところが改名しないと、末尾からの探索で内側の x:Sort 1x : \Sort{1}x:Sort1 が先に見つかり、yyy の型が Sort 1\Sort{1}Sort1 の要素であるかのように扱われて、誤った結果になります。改名すれば内側の束縛子は x′x'x′ になり、本体は外側の xxx を指したままです。

覚えておくこと

  • Infer\InferInfer は項の形に従い、Check\CheckCheck は推論してから IsDefEq\IsDefEqIsDefEq で比較します。T-Conv が現れるのは Check\CheckCheck の内部だけです。
  • Whnf\WhnfWhnf は、Π\PiΠ や宇宙が要求される場所で、型のいちばん外側の形を露わにします。
  • InferSort\InferSortInferSort は「この項は型か」を判定します。型であるためには、その型が宇宙に計算されなければなりません。
  • Freshen\FreshenFreshen は、文脈の項目をシャドーイングしてしまう束縛子を改名します。これは便宜のためではなく、正しさのために必要です。
  • src/typecheck.rs はアルゴリズムをほぼそのまま書き写したもので、約 100 行です。
